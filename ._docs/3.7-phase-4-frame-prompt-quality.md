# Phase 4: Frame Prompt Quality & Asset Linking (Task 4 + 4D.2 Fixes)

## Core Goal
Improve the specificity and quality of frame prompts (Stage 9) and verify that the correct assets are linked to start and end frames. Covers: body language/emotion detail, asset positioning/choreography, prompt length limits, shot list enhancement, and end frame asset verification.

---

## Problem Statement
Frame prompts currently describe *what's in the scene* but lack specificity on:
- **Body language & emotion**: How characters physically express themselves (posture, gesture, facial expression)
- **Asset positioning & choreography**: Where characters/props are in the frame relative to each other
- **Prompt length**: Prompts are being cut off due to enforced length caps, losing important detail

Additionally, the correct scene instance assets may not be reaching end frames, and the shot-to-asset assignment system needs verification.

---

## Current State

### Frame Prompt Structure (5-Part Formula)
`promptGenerationService.ts` uses a structured prompt with 5 sections:
1. CAMERA POSITION & FRAMING (shot type, angle, lens)
2. SUBJECT APPEARANCE (physical description from assets)
3. SPATIAL PLACEMENT & POSE (where subjects are in frame)
4. ENVIRONMENT & PROPS (location details, furniture, depth layers)
5. LIGHTING, COLOR & STYLE (key light, fill, color palette, mood)

### Current Prompt Length Limits
- **Frontend** (`Stage9PromptSegmentation.tsx`): Frame = 1000 chars (warn at 500), Video = 800 chars (warn at 400)
- **Backend** (`projects.ts`): Frame = 1500 chars, Video = 1000 chars
- **Generation output**: System prompt instructs max 1200 chars for frame prompts

### Shot List Data (Stage 7)
- `action`: Often just a line of dialogue with vague description
- `camera`: Free-text camera description
- `setting`: Location name
- `characters_foreground` / `characters_background`: Character names
- `dialogue`: Lines spoken
- `continuity_flags`: Explicit markers

### Shot-to-Asset Assignments
- `shot_asset_assignments` table with `presence_type`: throughout / enters / exits / passes_through
- `buildFrameReferenceManifests()` filters assets by presence type for start/end frames
- End frame reference resolution: `resolveEndFrameReferenceImages()` handles transformation swaps

## Implementation Notes

### 4A: Body Language & Emotion Enhancement

**Where**: `promptGenerationService.ts`, in the system prompt for `generateFramePrompt()`

The current system prompt instructs the LLM to describe subjects but doesn't explicitly request body language detail. Enhancement:

- Add to the Section 3 (SPATIAL PLACEMENT & POSE) instructions:
  ```
  For each visible character, describe:
  - Body posture (standing tall, hunched, leaning, seated with legs crossed)
  - Hand position and gesture (gripping, pointing, relaxed at sides, clenched fists)
  - Facial expression with specificity (not just "angry" but "jaw clenched, brow furrowed, nostrils flared")
  - Eye direction and gaze (looking directly at camera, glancing sideways, eyes downcast)
  - Physical state markers (sweating, breathing hard, trembling, relaxed)
  ```

- The LLM system prompt should also instruct: "Describe emotion through physical manifestation, not abstract labels. 'Grief' should become 'shoulders slumped, eyes red-rimmed, hands loosely holding a crumpled photograph.'"

**Source data**: The shot's `action` and `dialogue` fields contain emotional context. The LLM should infer physical expression from these.

### 4B: Asset Positioning & Choreography

**Where**: Same system prompt, Section 3

- Add instructions for spatial relationships:
  ```
  Describe the spatial arrangement of all visible subjects:
  - Frame position (left third, center, right edge, foreground, mid-ground, background)
  - Relative positioning (facing each other at arm's length, side by side, one behind the other)
  - Scale relationships (character in foreground large, background figures small)
  - Interaction geometry (leaning toward each other, back-to-back, one looking down at seated other)
  ```

- For multi-character shots, require explicit blocking: "Character A stands frame-left facing right, Character B sits frame-center looking up at A."

### 4C: Prompt Length Limit Changes

**Recommended approach**: Increase limits, add warnings instead of hard cuts.

| Limit | Current | Proposed |
|-------|---------|----------|
| Frame prompt (frontend display) | 1000 chars | 2000 chars |
| Frame prompt (frontend warning) | 500 chars | 1500 chars |
| Frame prompt (backend hard limit) | 1500 chars | 3000 chars |
| Frame prompt (LLM output instruction) | 1200 chars | 2000 chars |
| Video prompt (frontend display) | 800 chars | 1500 chars |
| Video prompt (frontend warning) | 400 chars | 1000 chars |
| Video prompt (backend hard limit) | 1000 chars | 2000 chars |

Frontend shows a yellow warning badge when prompt exceeds warning threshold. No truncation — user decides whether to shorten.

[UNRESOLVED] Whether longer prompts actually degrade image quality with current providers (Flux/Gemini). Should test empirically before committing to higher limits.

### 4D: Dynamic Prompt Optimization (Redundancy Removal)

The spec asks: can we remove details from prompts that are already conveyed by attached reference images?

**Approach**: Add a post-processing step after frame prompt generation:
1. For each reference image attached to the shot, note which asset it represents
2. For that asset's description in the prompt, reduce to only the *differences* from what the image shows (e.g., if the image shows the character in a blue dress but the scene description says "torn blue dress, soaking wet" — keep only "torn, soaking wet" since the dress itself is visible in the reference)
3. This is an LLM step: "Given this prompt and these reference image descriptions, remove redundant visual details that the image already conveys. Keep only scene-specific modifications, conditions, and spatial information."

[UNRESOLVED] Whether this optimization is worth the extra LLM call. May be better to just increase prompt length limits and accept some redundancy. Test both approaches.

### 4E: Shot List Enhancement (Stage 7)

**Where**: `backend/src/services/` — the shot list extraction/generation service

The shot list `action` field needs more detail. Enhancement to the extraction prompt:
- Include camera directions (pan, tilt, dolly, track)
- Include character positioning and movement within the shot
- Include environmental/lighting context changes
- Write in crew-note style: "WIDE SHOT — Alice enters frame-left, crosses to the bar. Camera TRACKS RIGHT to follow. Bob is already seated, back to camera. Warm amber lighting from overhead pendants."

This is a Stage 7 change that propagates benefits to Stages 9 and 10.

### 4F: End Frame Asset Linking Verification

**Investigation needed** (can be done as part of Phase 0 or here):

1. **Are end frame reference images different from start frame?**
   - Check `resolveEndFrameReferenceImages()`: does it correctly swap transformation post-images?
   - Check: for "enters" assets, do they appear ONLY in end frame refs?
   - Check: for "exits" assets, do they appear ONLY in start frame refs?

2. **Are end frames just copying start frame refs?**
   - The spec suspects this. Verify by logging the actual reference image arrays for start vs end frames of a shot with different assets.

3. **"Passes through" assets**
   - These should appear in the video prompt (text only) but NOT in start or end frame reference images
   - Verify `buildPresenceVideoContext()` handles this correctly

### 4G: Shot-to-Asset Assignment Quality

**Investigation needed**:
- How good is the current system at determining which assets appear in which shot?
- Is presence_type (throughout/enters/exits/passes_through) being set correctly?
- Is this done by LLM during shot list generation, or is it a separate assignment step?
- If assignment quality is poor, consider adding a user-facing UI in Stage 8 or 9 where users can correct shot-asset assignments

## Notables
- Prompt quality improvements (4A, 4B) are LLM system prompt changes — no new infrastructure needed, just prompt engineering. Test before/after with the same scene to measure improvement.
- The length limit changes (4C) should be tested empirically. If Flux/Gemini quality degrades with 2000+ char prompts, we may need the redundancy removal (4D) instead of just raising limits.
- Shot list enhancement (4E) affects ALL downstream stages. Changes here should be tested end-to-end before committing.
- The presence_type verification (4G) is critical for continuity. If "enters" and "exits" aren't being set correctly, start/end frame references will be wrong regardless of other fixes.
