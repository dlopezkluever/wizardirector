## Phase 1 — Fix Asset Inheritance Chain in Frame Generation (4D.2)

### Problem Statement
Generated frames in Stage 10 show no influence from master assets — characters, locations, and props look completely different from their established designs. The asset reference image chain from Stage 5 -> 8 -> 9 -> 10 is broken somewhere. This is the highest priority fix because all downstream prompt quality work (4C, structured prompts) is pointless if reference images never reach the image API.

### Core Goal
Verify and repair the full reference image pipeline so that Stage 10 frame generations visually reflect the master/scene-instance assets established in earlier stages. Add observability so users know when reference images fail.

### Relevant Files

**Backend (primary):**
- `backend/src/routes/projects.ts` ~lines 2212-2401 — Stage 9 generate-prompts endpoint; loads scene_asset_instances, builds reference_image_order, saves to shots table
- `backend/src/services/promptGenerationService.ts` ~lines 169-213 — `buildNumberedImageManifest()`: URL priority selection (matched_angle_url > image_key_url > master_image_url), silent skip on null
- `backend/src/services/frameGenerationService.ts` ~lines 517-532 — `fetchShotReferenceImages()`: reads reference_image_order from shots table, returns ReferenceImage[]
- `backend/src/services/image-generation/ImageGenerationService.ts` ~lines 291-352 — `executeJobInBackground()`: prepends identity refs to style capsule refs, passes to provider
- `backend/src/services/image-generation/NanoBananaClient.ts` ~lines 35-66 — `generateImage()`: downloads reference images, converts to base64, silently skips failures; ~lines 335-374 — `downloadAndConvertImage()`

**Frontend (secondary):**
- `src/components/pipeline/Stage9PromptSegmentation.tsx` — displays reference image order per shot
- `src/components/pipeline/Stage10FrameGeneration.tsx` — frame generation UI

### Current State

The architecture is correct — code exists to pass reference images through every stage. But investigation identified **4 failure points** where the chain silently breaks:

1. **Null image URLs** (`projects.ts:2249`): If both `selected_master_reference_url` AND `project_assets.image_key_url` are NULL, `master_image_url` becomes undefined. Asset is then silently excluded from the manifest.

2. **Silent exclusion** (`promptGenerationService.ts:184`): `if (!url) continue;` skips assets with no URL from the reference order. No warning logged. The LLM prompt text mentions the asset, but no visual reference accompanies it.

3. **Empty reference_image_order** (`frameGenerationService.ts:517-532`): If all assets had NULL URLs, the saved JSONB is empty/null. Stage 10 receives zero reference images. Frame generation proceeds text-only.

4. **Silent download failures** (`NanoBananaClient.ts:40-56`): Failed image downloads are caught and skipped. Supabase signed URL expiration, network issues, or malformed URLs cause references to vanish silently.

### Implementation Notes

**Step 1 — Add diagnostic logging throughout the chain:**
- In `buildNumberedImageManifest()`: log which assets were skipped and why (null URL fields)
- In `fetchShotReferenceImages()`: log the count and URLs being returned
- In `NanoBananaClient.generateImage()`: already logs failures, but aggregate into a structured result (success/fail counts per job)

**Step 2 — Fix URL expiration issue:**
- Investigate whether Supabase `image_key_url` values are signed (time-limited) or public permanent URLs
- If signed: re-resolve URLs at Stage 10 generation time by querying scene_asset_instances fresh, not relying on stale JSONB
- If public: verify URLs are accessible from the backend (network/CORS check)
- Recommended approach: at frame generation time, re-fetch current image URLs from scene_asset_instances rather than trusting the cached `reference_image_order` JSONB

**Step 3 — Surface failures to the user:**
- Modify `frameGenerationService.generateFrames()` return type to include per-shot diagnostics:
  - `referenceImagesRequested: number`
  - `referenceImagesLoaded: number`
  - `failedUrls: string[]` (for debugging)
- Display warning in Stage 10 UI when `loaded < requested`: "X of Y asset references failed to load — frames may not reflect your assets"

**Step 4 — Prevent null URL propagation:**
- In `projects.ts` generate-prompts endpoint: after building reference_image_order, warn if any scene_asset_instance with a non-null description has no image URL
- Consider: should assets without images still be excluded from the reference manifest? Or should we surface this as a Stage 8 issue ("Asset X has no image — generate or upload one before proceeding")?

**Step 5 — Verify style capsule interaction:**
- Check if visual style capsule reference images (appended after asset identity refs) are dominating the generation
- The style capsule images use `role: 'style'` but asset refs use `role: 'identity'` — verify the Gemini API actually distinguishes these
- If style images overwhelm identity refs, consider limiting style capsule images when asset refs are present

### Dependencies
- None — this is foundational and blocks all other phases.

### Notables
- The `reference_image_order` JSONB pattern (save URLs at Stage 9, read at Stage 10) is fragile by design. Any URL that changes or expires between these stages breaks silently. Consider whether this caching layer is worth keeping vs. always resolving fresh.
- The bug report mentions "a character's original master reference (from Stage 5) appeared in Stage 9/10 UI, rather than the scene-specific instance image (e.g. the gnome variant)" — this points to the URL priority in `buildNumberedImageManifest()` selecting `master_image_url` when `image_key_url` (scene instance) is NULL.
- Shot asset assignment auto-population creates `throughout` for ALL assets x ALL shots. This floods reference manifests with potentially irrelevant assets. Worth noting but not fixing here.
