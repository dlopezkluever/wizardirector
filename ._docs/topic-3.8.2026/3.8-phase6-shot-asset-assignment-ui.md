## Phase 6 — Shot Asset Assignment UI Improvements

### Problem Statement
The backend for shot-level asset assignments (presence_type: throughout/enters/exits/passes_through) and separate start/end frame reference manifests is architecturally sound. But the UI for managing these assignments needs improvement — users need better visibility into which assets are in which shots, and easier controls for adjusting presence types and end-frame asset overrides.

### Core Goal
Improve the Stage 9 shot asset assignment UI so users can clearly see and control: which assets appear in each shot, their presence type, and how start/end frame references differ (especially for transformation events).

### Relevant Files

**Backend (read-only — no changes expected):**
- `backend/src/services/shotAssetAssignmentService.ts` — `autoPopulate()`, CRUD for shot_asset_assignments
- `backend/src/services/promptGenerationService.ts` ~lines 222-267 — `buildFrameReferenceManifests()`: builds separate start/end frame manifests based on presence_type

**Frontend (primary):**
- `src/components/pipeline/Stage9PromptSegmentation.tsx` — main Stage 9 component
- Look for `ShotAssetPanel.tsx` or similar — per-shot asset assignment UI with presence_type dropdowns
- `src/lib/services/shotAssetAssignmentService.ts` — frontend API client

**Types:**
- `src/types/scene.ts` or `src/types/asset.ts` — `ShotAssetAssignment`, `PresenceType` enum

### Current State
- `ShotAssetPanel` exists with dropdowns to change presence_type per asset per shot
- Auto-populate creates `throughout` for ALL assets x ALL shots (potentially noisy)
- Presence changes trigger `invalidateStage9AndDownstream()`
- End-frame references are auto-computed from transformation events — no manual override UI exists

### Implementation Notes

**Step 1 — Investigate current ShotAssetPanel UI:**
- Read the component to understand current layout and capabilities
- Identify UX pain points: is it clear which assets are in which shots? Is presence_type easy to change?

**Step 2 — Improve asset-to-shot visibility:**
- Consider a matrix view: rows = assets, columns = shots, cells = presence_type (color-coded)
- Or a per-shot card view showing asset thumbnails with presence badges
- Show asset reference image thumbnails so users can see WHAT image is being sent

**Step 3 — Smarter auto-population defaults:**
- Currently ALL assets get `throughout` for ALL shots
- Locations should default to `throughout` (they're always visible)
- Characters should default based on shot `characters_foreground` / `characters_background` fields — if a character isn't mentioned in a shot, don't assign them
- Props could be smarter too — only assign if mentioned in shot `action` or `setting`

**Step 4 — End-frame reference visibility:**
- Show users what the end-frame reference manifest looks like (which assets, which images)
- For shots with within_shot transformation events: highlight the image swap (pre -> post transformation)
- Allow manual override of end-frame asset images (the spec mentions `end_frame_reference_image_order` is user-overrideable on the shots table)

**Step 5 — Inline asset reference editing:**
- Users should be able to swap which image (master ref vs scene instance) is sent as reference for a specific shot, without going back to Stage 8
- Add an image picker per asset-per-shot: shows available images (master, scene instance, angle variants, named shots) and lets user select

### Dependencies
- Phase 1 (4D.2) — fixes must land first so reference images actually work
- Phase 4 (location named shots) — if implemented, the inline picker needs to show named shot options

### Notables
- The matrix view (assets x shots) could become unwieldy for scenes with many shots and assets. Consider pagination or collapsible sections.
- Smarter auto-population (Step 3) could use the same LLM extraction that Stage 7 uses for character assignment — `characters_foreground`/`characters_background` fields already exist on shots.
- The inline asset reference editing (Step 5) partially addresses the concern from 3.7-tasks-part-3.md about being able to change asset references without navigating back to Stage 8.
- This phase is lower priority than 1-5 but directly improves the user experience of the asset-to-frame pipeline.
