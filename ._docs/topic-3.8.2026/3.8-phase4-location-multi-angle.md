## Phase 4 — Location Multi-Angle Named Shots (Topic 3)

### Problem Statement
A single location image is rarely sufficient for a dynamic story. Camera angles shift, characters move through different parts of a space, and the AI's inferences about unseen angles are unreliable. Characters already have a 4-angle variant system — locations need an analogous but more flexible system using user-defined named shots.

### Core Goal
Allow users to define multiple named location shots per location asset (e.g., `aerial_overview`, `room_A_medium`, `hallway_entrance`). These provide the image generator enough contextual reference to make logical, story-consistent background inferences. The goal is not perfection but **logical continuity** — backgrounds should make sense given what's established.

### Current State

**Characters:** Have `asset_angle_variants` table with 4 fixed angle types (front, side, three_quarter, back). `mapCameraToAngleType()` parses shot camera fields and selects the best matching angle variant. The matched variant URL takes highest priority in reference image manifests.

**Locations:** Single image per asset instance. No angle variants. No camera-to-location mapping. Treated as immutable environmental constants with `carry_forward=true`. Locations always use their single `image_key_url` or `master_image_url` regardless of shot camera angle.

### Implementation Notes

**Step 1 — Database: New table or extend existing:**

Option A (recommended): Create a `location_named_shots` table separate from `asset_angle_variants`:
```sql
CREATE TABLE location_named_shots (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_asset_id UUID REFERENCES project_assets(id) ON DELETE CASCADE,
  name TEXT NOT NULL,              -- user-defined: "aerial_overview", "hallway_entrance", etc.
  description TEXT,                -- what this angle/area shows
  image_url TEXT,
  image_prompt TEXT,               -- prompt used to generate this shot
  status TEXT DEFAULT 'pending',   -- pending/generating/completed/failed
  sort_order INTEGER DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

Why not extend `asset_angle_variants`: the existing table uses a fixed `angle_type` enum (front/side/three_quarter/back). Location shots need free-text names, not a fixed set. Different table keeps concerns clean.

**Step 2 — Generation workflow:**
- User creates location asset in Stage 5 with initial image (the "primary" shot)
- User opens a "Named Shots" dialog (similar to AngleVariantsDialog but with free-text naming)
- User adds named shots: types a name, optionally a description of what the angle/area shows
- Generation: uses the primary location image as reference + the name/description as prompt guidance to generate consistent variants
- Batch generation: generate all pending named shots at once
- User can also upload custom images for any named shot

**Step 3 — Camera-to-location-shot mapping:**
- Create `mapCameraToLocationShot()` in promptGenerationService.ts
- Unlike characters (deterministic 4-angle mapping), location mapping is fuzzy: needs LLM or heuristic matching between shot camera/setting description and available named shots
- Simple heuristic first: keyword matching between shot `camera`+`setting` fields and named shot `name`+`description`
- Fallback: if no match, use primary location image (current behavior)

**Step 4 — Integrate into reference image manifests:**
- Modify `buildNumberedImageManifest()` to check for matched location named shots
- URL priority for locations becomes: `matched_location_shot_url > image_key_url > master_image_url`
- Modify `enrichAssetsWithAngleMatch()` to also handle locations (currently skips non-characters)

**Step 5 — Frontend UI:**
- New dialog component: `LocationNamedShotsDialog.tsx` (modeled on AngleVariantsDialog)
- Free-text name input + optional description
- Grid display of generated named shots
- Generate all / generate individual buttons
- Accessible from Stage 5 location asset cards

**Step 6 — Scene instance inheritance:**
- Named shots live at the project_asset level (like angle variants)
- Scene instances reference the same named shots — no per-scene duplication needed
- If a scene has a location transformation (rare), the transformed instance could have its own named shots [UNRESOLVED — defer to later if needed]

### Dependencies
- Phase 1 (4D.2) should land first — reference images must work before adding more image types
- Requires a database migration (prompt user, never run directly)
- No dependency on Phase 2 or 3 — can be done in parallel with prompt work

### Notables
- The camera-to-location mapping is the hardest part. Characters have 4 fixed angles that map cleanly to camera descriptions. Locations have arbitrary user-defined names. Start with keyword matching and iterate.
- Location named shots are project-level, not scene-level. A location's shots are consistent across all scenes (unlike characters who may transform). If a location changes in a scene (e.g., room gets destroyed), that's a transformation event — the named shots would need post-transformation variants. [UNRESOLVED — defer complexity]
- Generation quality depends on the primary image. If the user generates a front view of a building, generating a consistent interior from that is unreliable. Guide users: "Start with the most representative angle, then generate variants."
- This feature is the most complex of the five. Consider shipping a minimal version (named shots + manual upload) before building automatic camera matching.
