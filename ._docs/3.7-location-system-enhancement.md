# 3.7 Location System Enhancement — Master Specification

## Problem Statement

Location assets are fundamentally different from characters and props. Characters and props are object-centric — you attach an image of a thing and it appears in the frame. Locations are space-centric — the reference image is one specific view of a space, but frames need to represent that same space from many angles, distances, and positions. The reference and the output share the same world, but not the same view. That's a much harder inference problem.

### The Three Failure Modes This System Solves

1. **Angle Mismatch** — The reference is an aerial shot but the scene needs eye-level. The generator guesses the ground-level view and gets it wrong.
2. **Partial Space Coverage** — The reference shows one wall of a room. A reverse-angle shot has zero reference for what the opposite wall looks like. The generator hallucinates.
3. **Sub-location Drift** — A scene heading says "INT. APARTMENT" but characters move between the living room, kitchen, and hallway. A single reference image can't anchor all of those distinct spaces.

### Why Prompt Engineering Alone Can't Fix This

- Language is lossy for spatial description
- The same room generated from five different prompts looks like five different rooms (color shift, proportion drift, architectural inconsistency)
- The generator has no memory of prior frames — each background is generated independently
- The fix must be **primarily visual reference-based**, with prompts playing a supporting role

---

## Architecture Overview

The location system enhancement has five interconnected layers:

1. **Sub-location Precision** — Script and dependency extraction produce precise location headings (room-level, not building-level)
2. **Camera Directions** — Each sub-location has named directional reference images (establishing + wall/direction views)
3. **Per-Shot Direction Assignment** — Each shot is assigned a specific camera direction, enabling the system to select the right reference image
4. **Coverage Analysis** — Advisory system flags gaps before generation
5. **Established Views** — Approved generated frames become future reference images (industry-standard "hero frame" pattern)

## Layer 1: Sub-location Precision in the Script

### Current Problem

Scripts currently produce general location headings:
```
INT. GINGERBREAD HOUSE - DAY
```

This extracts as a single location asset "Gingerbread House" in Stage 4. But the scene may include action in the kitchen, hallway, and front yard — all with completely different visual contexts.

### Solution: Spatially Explicit Script Generation

**Stage 3→4 (Script Generation) gets two new rules:**

1. **Precise scene headings** — Always specify the exact room or area within a location:
   ```
   INT. GINGERBREAD HOUSE - KITCHEN - DAY
   INT. GINGERBREAD HOUSE - HALLWAY - CONTINUOUS
   EXT. GINGERBREAD HOUSE - FRONT YARD - CONTINUOUS
   ```

2. **Spatially explicit action lines** — All action/paragraph text must anchor characters to specific positions in the space. Not "They argue." but "They argue across the kitchen counter. He storms out through the hallway toward the front door." Every action beat should describe WHERE characters are and WHERE they move.

**For scenes where characters move between sub-locations:** The script splits into separate scene headings using the `CONTINUOUS` slug to maintain narrative flow:
```
INT. GINGERBREAD HOUSE - KITCHEN - DAY
Hansel backs away from the witch, knocking a chair aside.

INT. GINGERBREAD HOUSE - HALLWAY - CONTINUOUS
He crashes through the hallway, knocking a shelf of candy jars to the floor.

EXT. GINGERBREAD HOUSE - FRONT YARD - CONTINUOUS
He bursts through the gingerbread door into the clearing.
```

This is standard screenplay format. Each heading cleanly assigns a sub-location, and Stage 4 dependency extraction creates separate location assets for each.

**For subtle positional changes within a single sub-location** (e.g., "the hero walks to the corner of the room") — the sub-location doesn't change. What changes is the camera direction. Stage 7 handles this through per-shot camera direction assignment based on the spatially explicit action text.

### Pipeline Impact

| Stage | Change |
|-------|--------|
| Stage 3→4 (Script Gen) | Prompt update: require precise room/area in scene headings + spatially explicit action lines |
| Stage 4 (Dependency Extraction) | Extracts `expectedLocation` with sub-location precision (e.g., "Gingerbread House - Kitchen" not just "Gingerbread House") |
| Stage 5 (Assets) | Each sub-location is its own location asset with its own reference images |

### Relevant Files

| File | Change |
|------|--------|
| Backend script generation prompts (Stage 3→4) | Add sub-location precision rules and spatial explicitness requirements |
| `backend/src/services/sceneDependencyExtraction.ts` | Update extraction to handle compound location headings (`LOCATION - SUBLOCATION`) |
| `src/types/scene.ts` → `Scene.expectedLocation` | Will now contain sub-location strings like "Gingerbread House - Kitchen" |

## Layer 2: Camera Directions (Multi-View Location References)

### Concept

Each location asset gets a set of named **camera direction** reference images — specific viewpoints of the space that the system can intelligently select from per-shot. This replaces the current single-image-per-location model.

The term "camera direction" is universal — it works for both interiors ("stove wall", "window wall") and exteriors ("facing the house", "facing the forest"). Each direction can have a user-defined alias for clarity.

### Data Model

**New table: `location_views`** (separate from `asset_angle_variants`, which is character-specific)

```sql
CREATE TABLE location_views (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_asset_id UUID NOT NULL REFERENCES project_assets(id) ON DELETE CASCADE,
  name            TEXT NOT NULL,           -- system name: "establishing", "direction_1", "direction_2", etc.
  alias           TEXT,                    -- user-defined label: "stove wall", "window side", "facing the house"
  description     TEXT,                    -- what this view shows
  view_type       TEXT NOT NULL,           -- 'establishing' | 'direction'
  camera_distance TEXT DEFAULT 'wide',     -- 'wide' | 'medium' | 'close'
  camera_height   TEXT DEFAULT 'eye_level',-- 'eye_level' | 'high_angle' | 'low_angle' | 'overhead' | 'ground_level'
  image_key_url   TEXT,                    -- Supabase storage URL
  is_primary      BOOLEAN DEFAULT false,   -- the default fallback view (one per location)
  source          TEXT DEFAULT 'user',     -- 'user' (uploaded/generated in Stage 5/8) | 'established' (locked from generated frame)
  established_from_scene TEXT,             -- if source='established': which scene/shot it came from
  sort_order      INT DEFAULT 0,
  created_at      TIMESTAMPTZ DEFAULT now(),
  updated_at      TIMESTAMPTZ DEFAULT now(),
  UNIQUE(project_asset_id, name)
);
```

**TypeScript interface:**

```typescript
interface LocationView {
  id: string;
  project_asset_id: string;
  name: string;                           // "establishing", "direction_1", "direction_2"
  alias?: string;                         // "stove wall", "window side"
  description?: string;                   // "Kitchen seen from the stove side, facing the window"
  view_type: 'establishing' | 'direction';
  camera_distance: 'wide' | 'medium' | 'close';
  camera_height: 'eye_level' | 'high_angle' | 'low_angle' | 'overhead' | 'ground_level';
  image_key_url?: string;
  is_primary: boolean;
  source: 'user' | 'established';
  established_from_scene?: string;
  sort_order: number;
  created_at: string;
  updated_at: string;
}
```

### Default View Proposals

When a location asset is created or when the user clicks "Suggest Views," the system proposes views based on INT/EXT:

| Location Type | View 1 | View 2 | View 3 |
|---------------|--------|--------|--------|
| **Interior** (`INT.`) | Establishing (overhead, wide) — full room from above | Direction 1 (eye_level, wide) — one wall | Direction 2 (eye_level, wide) — opposite wall (reverse) |
| **Exterior** (`EXT.`) | Establishing (wide) — full view of the location | Direction 1 (eye_level, wide) — approach/facing location | Direction 2 (eye_level, wide) — reverse/from location outward |

**3 views is the default.** Users can add more directions (Direction 3, 4, etc.) if the space requires it, but the system never proposes more than 3 by default to keep friction low.

Each direction gets a user-defined alias. Examples:
- Interior: Direction 1 alias = "stove and counter wall", Direction 2 alias = "window and breakfast nook"
- Exterior: Direction 1 alias = "facing house facade", Direction 2 alias = "facing the forest"

### Where Views Are Managed

**Stage 5 is the primary location** for defining views — this is where the user builds their location asset library. But Stage 5 is **not a gate**. Users can:
- Define all views in Stage 5 upfront (ideal)
- Define just the establishing shot in Stage 5 and defer the rest
- Add/edit views from Stage 8 as well (not restricted to Stage 5)

Many users will be lazy in Stage 5 — the system accommodates this by allowing view creation in Stage 8 and flagging gaps via the coverage advisory.

**Stage 8 can also add scene-specific view overrides** (e.g., "this scene's kitchen has smoke damage") — the same override pattern used for character descriptions today.

### View Generation Strategy

When the user wants to generate a view image:

1. Send the **establishing/primary image** as a style reference alongside a text prompt describing the desired view
2. Include the location's text description in the prompt
3. Prompt explicitly describes the desired angle: "Same Victorian kitchen seen from the opposite wall, eye-level perspective looking back toward the stove and window. Maintain same color palette, architectural details, and lighting conditions."

**Important caveat (from research):** AI is unreliable at generating consistent alternate angles of complex environments. Products and simple objects work well; rooms with many objects do not. The UI should frame view generation as a **starting point that may need curation**, not a "click and done" solution. User uploads are more reliable for critical views.

### Batch View Generation

When clicking "Generate Missing Views" or "Suggest & Generate Views":

1. System analyzes uncovered shot clusters from the scene's shot list (see Layer 4: Coverage Analysis)
2. Proposes specific views to generate, pre-filled with name, alias, and description
3. User reviews, edits, removes, or confirms each proposed view
4. For each confirmed view: generates using the establishing/primary image as reference + view description as prompt
5. User reviews results, can regenerate any that don't match expectations

The proposals stay minimal — informed by the shot list but capped at what's actually needed.

## Layer 3: Per-Shot Camera Direction Assignment

### Concept

Each shot in the shot list gets assigned a specific camera direction from the available location views. This tells the system exactly which reference image to use when generating that shot's frame.

### Shot Metadata Extension

The `Shot` interface gains structured camera metadata:

```typescript
interface Shot {
  // ... existing fields ...
  setting: string;
  camera: string;                                   // existing free-text: "MS - eye level static"

  // New structured fields (generated at Stage 7, parsed as fallback)
  camera_distance?: 'wide' | 'medium' | 'close';
  camera_height?: 'eye_level' | 'high_angle' | 'low_angle' | 'overhead' | 'ground_level';
  camera_movement?: string;
  camera_direction_id?: string;                     // FK to location_views.id — assigned camera direction
}
```

### How Camera Direction Gets Set

**Two-track approach (generate + parse):**

1. **Stage 7 (shot generation):** The LLM prompt is updated to output structured camera metadata alongside the free-text `camera` field. The prompt also receives the location's available camera directions (from Stage 5) so it can assign the most appropriate direction per shot based on narrative context:

   ```
   Stage 7 LLM context injection:

   "Location: GINGERBREAD HOUSE - KITCHEN
    Available camera directions:
      - Direction 1 (alias: 'stove and counter wall'): Stove, marble countertops, copper pots hanging from rack
      - Direction 2 (alias: 'window and breakfast nook'): Bay window with morning light, small breakfast table

    For each shot, assign `camera_direction` to the most appropriate direction
    based on where the camera would be facing given the action."
   ```

2. **`parseCameraMetadata()` function (fallback):** For legacy shots or manually edited camera fields, a parsing function extracts structured metadata from the free-text camera string. Builds on existing `mapCameraToAngleType()` logic:

   ```typescript
   parseCameraMetadata('WS - high angle crane down')
   → { distance: 'wide', height: 'high_angle', movement: 'crane_down' }

   parseCameraMetadata('CU - eye level static')
   → { distance: 'close', height: 'eye_level', movement: 'static' }
   ```

### Direction Assignment Editing

The camera direction assignment for each shot is **editable across multiple stages** — same underlying data, reactive everywhere:

- **Stage 7** — User can review/edit direction assignments after shot list generation
- **Stage 8** — Shot-to-direction assignment table as part of the coverage panel
- **Stage 9** — Visible and editable during prompt review, last chance before generation
- **Stage 10** — Visible during frame generation review

When the user changes a direction assignment in any stage, it updates the shot record and reflects everywhere else.

### Matching Logic (`matchShotToLocationView()`)

When the LLM doesn't assign a direction (or for retroactive matching), the system uses deterministic metadata matching:

```
1. Parse shot's camera field → { distance, height }
2. Score each available location view:
   - camera_height match: +2 points
   - camera_distance match: +1 point
   - action text contains alias keywords (e.g., "stove" matches alias "stove wall"): +3 points
3. Pick highest-scoring view
4. If score = 0 → use is_primary (establishing) view as fallback
5. Store assignment on shot (user can override)
```

No LLM involved — deterministic, fast, no API cost.

### View Reuse Across Shots

A single camera direction can (and will) be assigned to many shots. If 8 shots all face "Direction 1" of the kitchen, they all reference the same Direction 1 image. This is the primary mechanism for visual consistency.

### Graceful Degradation

When no perfect view match exists for a shot's camera angle:

1. Use the **closest available** direction as the image reference
2. The prompt explicitly states the **delta** between the reference and the desired shot:
   > "The attached reference shows the kitchen at eye level. Frame this shot from a HIGH ANGLE looking down at the same space. Maintain the same color palette, architectural details, and spatial layout."
3. The coverage advisory in Stage 8 flags this so the user can create the missing view before spending generation credits

## Layer 4: Coverage Analysis (Advisory)

### Concept

Before generation, the system analyzes all shots for each location and maps them against available camera directions. It produces a non-blocking advisory showing coverage status and gaps.

### Location & Timing

The coverage advisory appears in **Stage 8** (Visual Definition), alongside the shot list. It's a panel or section within the existing Stage 8 UI. It is **non-blocking** — the user can proceed to generation with gaps, but the system clearly communicates the risk.

### How It Works

1. For each location in the scene, gather all shots that reference it
2. Group shots by their assigned camera direction
3. For each group, check if the assigned direction has a reference image
4. Produce a coverage status:

```
Stage 8 - Location Coverage: GINGERBREAD HOUSE - KITCHEN

✅ Direction 1 "stove wall" (6 shots) — reference image available
⚠️ Direction 2 "window side" (3 shots) — no reference image
⚠️ Unmatched high-angle shots (1 shot) — closest match: Direction 1 (quality may vary)

[Generate Missing Views]  [Proceed Anyway]
```

### Coverage States

| State | Icon | Meaning |
|-------|------|---------|
| Covered | ✅ | Direction has a reference image and matching shots |
| Missing reference | ⚠️ | Direction assigned to shots but has no image — will use closest available |
| No direction match | ⚠️ | Shot's camera angle doesn't closely match any available direction — will use primary/establishing as fallback |
| Fully covered | ✅✅ | All shots have well-matched direction references |

### "Generate Missing Views" Action

When the user clicks this:
1. System identifies the uncovered directions/clusters
2. Auto-proposes views to fill the gaps (pre-filled name, alias, description based on shot analysis)
3. User reviews and confirms
4. Batch generation runs (establishing image as style reference + view description as prompt)

## Layer 5: Established Views (Hero Frame Locking)

### Concept

When a generated frame produces a good background for a specific camera direction, the user can **lock** that frame as an "established view" — a new location view reference that all subsequent shots from the same direction will use.

This is the industry-standard "hero frame" pattern. Research confirms it's the single most impactful technique for achieving visual consistency across AI-generated frames.

### Prominence

This is a **core feature**, not an optional add-on. It is prominently surfaced in the frame review workflow:

1. After a frame is generated and approved in Stage 10, the system checks if it fills a coverage gap
2. If it does, the system proactively suggests locking:
   ```
   ✅ Frame approved for Shot 3

   📌 This fills a coverage gap!
     Location: Kitchen
     Direction: Direction 1 "stove wall"
     Currently: no established view for this direction

     [🔒 Lock as Established View]  [Skip]
   ```
3. If the direction already has a reference, the lock option is still available but not proactively suggested — user discovers it as a secondary action

### How Locking Works

1. User clicks "Lock as Established View" on an approved generated frame
2. System creates a new `location_views` record:
   - `source: 'established'`
   - `established_from_scene`: scene number + shot ID for audit trail
   - `image_key_url`: the generated frame's image URL
   - Camera metadata inherited from the shot that produced it
3. If a direction already has a user-uploaded reference, the established view can optionally replace it or coexist (user choice)
4. All future shots assigned to that direction will now use the established frame as their reference

### Why This Works

The first time a kitchen at eye-level is generated, the AI invents details (furniture placement, wall color, specific fixtures). The second time, it references its own prior output — achieving visual consistency without the user uploading anything extra. The location's reference library grows organically during production.

### Stage 8 Coverage Panel Integration

Established views appear in the coverage panel with distinct labeling:
```
✅ Kitchen establishing (user uploaded)
✅ Kitchen Direction 1 "stove wall" (ESTABLISHED — Scene 2, Shot 3)
⚠️ Kitchen Direction 2 "window side" (no reference)
```

## Prompt Generation Changes

### Reference Image Strategy

**Research finding:** Google's Imagen API has no "location" or "environment" subject reference type. `REFERENCE_TYPE_SUBJECT` only supports `PERSON`, `ANIMAL`, `PRODUCT`. For locations, we use `REFERENCE_TYPE_STYLE` — this captures visual tone, color palette, and atmosphere, which is exactly what environments need.

**Per-frame reference image manifest for locations:**

Each frame gets **2 location reference images** (research confirms 2-3 is the sweet spot; more causes quality degradation):

1. **Best-matching direction view** (MAIN REFERENCE) — the camera direction assigned to this shot
2. **Establishing view** (SPATIAL CONTEXT) — always included to provide overall spatial layout and color palette anchor

```
REFERENCE IMAGES (attached alongside this prompt during image generation):
Image #1: Alice (character, front) — REFERENCE_TYPE_SUBJECT
Image #2: Kitchen - Direction 1 "stove wall" (location, MAIN REFERENCE) — REFERENCE_TYPE_STYLE
Image #3: Kitchen - establishing (location, SPATIAL CONTEXT) — REFERENCE_TYPE_STYLE
Image #4: Old clock (prop) — REFERENCE_TYPE_SUBJECT
```

### Imagen API Call Structure

```json
{
  "instances": [{
    "prompt": "A cinematic frame of [2] standing in the [1] style kitchen...",
    "referenceImages": [
      {
        "referenceType": "REFERENCE_TYPE_STYLE",
        "referenceId": 1,
        "referenceImage": { "bytesBase64Encoded": "<location_direction_view>" }
      },
      {
        "referenceType": "REFERENCE_TYPE_SUBJECT",
        "referenceId": 2,
        "referenceImage": { "bytesBase64Encoded": "<character_image>" },
        "subjectImageConfig": {
          "subjectType": "PERSON",
          "subjectDescription": "Alice"
        }
      }
    ]
  }]
}
```

### Graceful Degradation in Prompts

When the reference image doesn't perfectly match the shot's camera angle, the prompt includes an explicit delta description:

> "The attached location reference (Image #2) shows the kitchen at eye level from the stove side. This shot requires a HIGH ANGLE view looking down at the same space. Use the reference for spatial context, color palette, and architectural details, but frame from above."

### Scene Bible Pattern

The existing `buildAssetContext()` function in `promptGenerationService.ts` already injects location descriptions as repeatable text into every prompt. This should be strengthened to include:

- The specific direction alias and description for the assigned view
- Explicit architectural and material descriptors that must remain consistent
- Time-of-day and lighting descriptors locked per scene

This "scene bible" approach is the most reliable technique for environment consistency, according to industry practitioners.

### Veo Video Generation Note

Veo 3.1 **cannot combine first-frame mode with reference images** in the same API call. Since our pipeline uses first-frame mode for video generation (the generated frame IS the starting frame for video), the quality of Stage 10's frame generation is the critical determinant of video background quality. Every investment in better location view matching directly improves video output.

| `backend/src/services/imageGenerationService.ts` | Use `REFERENCE_TYPE_STYLE` for location refs in Imagen API calls |

## Complete Pipeline Flow (End to End)

### Stage 3→4: Script Generation
- Script uses precise scene headings: `INT. GINGERBREAD HOUSE - KITCHEN - DAY`
- Action lines are spatially explicit: "She crosses to the window and peers out"
- Location changes within a sequence use `CONTINUOUS` slugs with new headings
- **No "dynamic scene" flags needed** — just precise headings and explicit action text

### Stage 4: Dependency Extraction
- Extracts sub-location-precision `expectedLocation` values: "Gingerbread House - Kitchen"
- Each distinct sub-location becomes a separate location dependency

### Stage 5: World Building (Primary View Management)
- Each sub-location is its own location asset
- New "Camera Directions" section per location asset:
  - System suggests 3 default views based on INT/EXT
  - User names/aliases each direction
  - User uploads or generates reference images per direction
  - Establishing shot is recommended but nothing is required — user can defer
- **Not a gate** — users can leave with 0 views and handle it in Stage 8

### Stage 7: Shot List Generation
- LLM receives available camera directions per location as context
- LLM outputs structured camera metadata per shot: `camera_distance`, `camera_height`, `camera_movement`
- LLM assigns `camera_direction_id` per shot based on narrative context
- `parseCameraMetadata()` serves as fallback parser for legacy/edited camera fields
- User can review and edit direction assignments in Stage 7

### Stage 8: Visual Definition
- **Coverage Advisory Panel** shows per-location coverage status
- **Shot-Direction Assignment Table** shows each shot's assigned direction with thumbnail preview
- User can override direction assignments
- User can add new camera directions directly from Stage 8 (not restricted to Stage 5)
- "Generate Missing Views" button auto-proposes and batch-generates uncovered directions
- Scene-specific view overrides available (e.g., damaged version of a location)

### Stage 9: Prompt Review
- Direction assignments visible and editable (last chance before generation)
- Prompt preview shows which 2 location reference images will be sent per frame
- Delta descriptions visible for imperfect matches

### Stage 10: Frame Generation
- `enrichAssetsWithAngleMatch()` selects the assigned direction's image for each shot
- Prompt manifest includes 2 location refs: matched direction (MAIN) + establishing (CONTEXT)
- Location refs sent as `REFERENCE_TYPE_STYLE` in Imagen API
- Delta descriptions included in prompt when reference doesn't perfectly match shot angle
- **After frame approval:** "Lock as Established View" prominently offered (proactive suggestion when filling a gap)
- Established views fed back into the location's view library for future shots

## Research-Backed Design Decisions

These decisions are informed by web research on AI image generation, Google API documentation, and industry practitioner experience:

| Decision | Research Basis |
|----------|----------------|
| Use `REFERENCE_TYPE_STYLE` for location refs | Google Imagen has no "location" subject type. Style references capture visual tone and palette — appropriate for environments. |
| 2 location refs per frame (matched + establishing) | Research shows diminishing returns and quality degradation beyond 3-4 references. 2 is the sweet spot. |
| Established Views as core feature | Industry-standard "hero frame" pattern. Most impactful technique for consistency per filmmaker workflows. |
| Temper batch generation expectations | AI is unreliable at generating consistent alternate angles of complex environments. Works for products, not rooms. User uploads and curation are more reliable. |
| Scene bible pattern (repeatable descriptions) | Most reliable technique for environment consistency. Lock descriptors and repeat identically across prompts. |
| Frame quality is everything for video | Veo 3.1 cannot combine first-frame mode with reference images. The generated frame IS the environment anchor for video. |
| Metadata matching over LLM matching | Deterministic, fast, no API cost. LLM matching is expensive and adds latency for marginal accuracy gain. User override handles edge cases. |
| 3 default views (establishing + 2 directions) | Practitioners report that establishing + shot/reverse-shot covers most narrative shot angles. More creates friction without proportional benefit. |

## Future Considerations (Not In Scope)

These are recognized opportunities that may be worth pursuing later, but are explicitly **not part of this specification**:

- **Zone hierarchy**: If the flat views model proves insufficient for very complex locations (e.g., multi-room mansions), views could be grouped into named zones. The `location_views` table could gain a `zone_label` column for grouping without a separate table.
- **LLM-based matching**: If metadata matching proves too coarse, a lightweight LLM classification step could improve shot-to-view matching accuracy. Build the metadata matcher first and evaluate before adding LLM cost.
- **ControlNet / IP-Adapter integration**: For maximum environment control, these Stable Diffusion ecosystem tools offer granular style and structure conditioning. Requires separate infrastructure from Google's APIs.
- **3D environment pre-visualization**: Using tools like Unreal Engine to generate 360° panoramas of environments, then applying style transfer for inherently consistent backgrounds.
- **Auto-lock established views**: Automatically locking the first approved frame per direction. Currently manual-only to preserve user control; could be offered as a preference toggle.
