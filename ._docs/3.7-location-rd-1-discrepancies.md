 Discrepancy Report: Plan vs. Implementation

  Core Implementation (Phases A–H): COMPLETE

  All 8 phases are implemented with the correct data model, interfaces, endpoints,  
  services, components, and tests. The foundational architecture is solid and       
  matches the master plan.

  Gaps Found

  1. Stage 7 Direction Assignment Editing UI — MISSING

  Plan says (Layer 3, p.297): "Stage 7 — User can review/edit direction assignments 
  after shot list generation"

  Reality: Stage7ShotList.tsx has no UI for viewing or editing camera_direction_id  
  on shots. Users see the raw camera text field but cannot review or reassign the   
  structured direction the LLM chose. The earliest place to edit direction
  assignments is Stage 8's LocationCoveragePanel.

  Impact: Medium. The LLM assigns directions automatically during extraction, and   
  Stage 8 allows correction — but the user loses the immediate-review opportunity   
  right after shot generation.

  ---
  2. Stage 9 Direction Visibility/Editing — MISSING

  Plan says (Layer 3, p.295–296): "Stage 9 — Visible and editable during prompt     
  review, last chance before generation" and (Pipeline Flow, p.577–578): "Prompt    
  preview shows which 2 location reference images will be sent per frame. Delta     
  descriptions visible for imperfect matches."

  Reality: Stage9PromptSegmentation.tsx has no UI for viewing direction assignments,   no preview of which 2 location reference images will be attached, and no display 
  of delta descriptions. Direction data flows through the backend prompt generation 
  correctly, but the user has no visibility into it at Stage 9.

  Impact: Medium. The prompts are generated correctly on the backend, but the user  
  cannot verify or adjust the location reference strategy before committing to      
  generation.

  ---
  3. Scene-Specific View Overrides — MISSING

  Plan says (Layer 2, p.182–183): "Stage 8 can also add scene-specific view
  overrides (e.g., 'this scene's kitchen has smoke damage') — the same override     
  pattern used for character descriptions today."

  Reality: LocationCoveragePanel shows coverage and allows direction reassignment,  
  but has no mechanism for per-scene view overrides (e.g., an alternate "damaged    
  kitchen" image for a specific scene while other scenes use the normal kitchen).   

  Impact: Low. This is an edge-case feature for advanced users. The system works    
  correctly without it for the vast majority of use cases.

  ---
  4. Batch Generation Proposal Flow — SIMPLIFIED

  Plan says (Layer 4, p.380–383): "System identifies uncovered directions/clusters →   Auto-proposes views to fill gaps (pre-filled name, alias, description) → User    
  reviews and confirms → Batch generation runs"

  Reality: LocationCoveragePanel shows missing directions with a "Generate N Missing   Views" button that immediately triggers sequential generation — no intermediate  
  proposal/review dialog. Users also get per-direction Sparkles buttons for
  individual generation.

  Impact: Low. The simplification is arguably better UX — the directions already    
  exist (created by Stage 7 or manually), so there's nothing to "propose." The      
  one-click approach reduces friction. The plan's proposal flow was designed for a  
  case where directions don't exist yet, but in practice Stage 7's stage7_inferred  
  creation ensures they always do.

  ---
  5. LocationViewsGrid.tsx — RENAMED

  Plan says: New file src/components/pipeline/Stage5/LocationViewsGrid.tsx.

  Reality: Implemented as src/components/pipeline/LocationViewsDialog.tsx instead.  
  Functionally equivalent — provides grid of view cards, image upload, alias        
  editing, primary toggle, source badges.

  Impact: None. This is a design-time naming change, not a functional gap.
