The Location Asset Problem — Deep Dive

The Core Tension
Every other asset type in the pipeline — characters, props — is essentially object-centric. You attach an image of a thing, and that thing appears in the frame. The image generator's job is to place and render that object. The reference image and the output share the same subject.
Location assets are fundamentally different. The reference image you submit is one specific view of a space — but the generated background needs to represent that same space from potentially dozens of different angles, distances, and focal points across a scene. The reference and the output share the same world, but not the same view of it. That's a much harder inference problem.

The Three Distinct Failure Modes
1. Angle Mismatch
The submitted location image is an aerial or establishing shot, but the scene is shot at eye level. The image generator now has to infer what a ground-level view of that space looks like from a single bird's-eye reference. It will guess — and it will often guess wrong. The color palette might carry over. Maybe a few recognizable elements. But the feel of being inside that space won't be there.
2. Partial Space Coverage
The submitted image shows one corner or one aspect of a room — say, a fireplace wall in a living room. But the shot requires a view from the opposite side, looking back toward that fireplace. The generator has zero reference for what that reverse angle contains. It will hallucinate furniture, wall colors, windows — none of which the user chose or approved.
3. Sub-location Drift
This is the subtlest one. The header location stays the same (e.g. "INT. APARTMENT — LIVING ROOM") across many shots, but narratively the characters move — they sit on the couch, walk to the kitchen doorway, argue near the window, end up in the hallway. Each of those positions implies a meaningfully different background. A single location asset image can't anchor all of those sub-positions. Without sub-location coverage, the AI treats each shot as the same static background, which immediately breaks visual realism.

Why Prompt Engineering Alone Can't Fix This
The instinct is to solve this with better text prompts — describe the angle, describe the framing, describe what's in the background. And prompt engineering does help at the margins. But there's a hard ceiling:

Language is lossy for spatial description. Saying "shot from the left side of the room looking right, hardwood floors, brick wall visible" gives the generator some constraints, but it's still inventing most of the room from scratch.
Consistency breaks across shots. Even if each individual frame's background looks decent, the same room generated from five different prompts will subtly (or not so subtly) look like five different rooms. Colors shift, proportions drift, architectural details change.
The generator has no memory of prior frames by default. Without a visual anchor, each background generation is essentially independent. You're relying on prompt repetition to create consistency, which is unreliable.

The fix has to be primarily visual reference-based, with prompts playing a supporting role — not the other way around.

What an Adequate Location Asset System Actually Needs
The goal is to give the image generator enough visual context that its inferences are constrained and logical, not open-ended hallucinations. That means multi-view coverage of each location, organized in a way the system can reason about.
Required View Types (proposed minimum set):
View LabelDescriptionestablishingWide/aerial overview — shows the full space, layout, scaleeye_level_primaryThe main "default" shot angle — medium, straight-oneye_level_secondaryA second common angle — e.g. reverse shot, or 90° rotationdetail_focal_pointsClose-up of key elements that appear in shots (fireplace, desk, door)sub_location_[name]Distinct zones within the space if characters move between them
Not all of these need to be required for every location — but the system should prompt the user to provide what's relevant based on the shot list for that scene. If the shot list includes a reverse angle, the system should flag: "No secondary angle reference found for this location — generation quality may be reduced."
Named & Tagged, Not Just Uploaded
Each submitted image needs metadata:

View type (from the taxonomy above)
Sub-location label if applicable (e.g. kitchen_doorway, couch_area)
Shot alignment — what camera distance/angle does this image most closely represent (wide, medium, close; eye level, high angle, low angle)

This metadata is what allows the frame prompt generator in Stage 10 to select the most relevant location reference image for each shot — not just always defaulting to the first uploaded image.

The Selection Logic Problem (Stage 9 → 10)
Right now, one location image gets attached. What we actually need is a matching system that looks at each frame's shot metadata (camera angle, distance, position in the scene) and selects the most appropriate location reference from the multi-view set.
Something like:

Frame calls for a MEDIUM | EYE LEVEL | near the window shot →
System looks at available location views →
Selects eye_level_primary and detail_focal_point: window as the reference images for that frame

This means the location asset isn't a single image anymore — it's a referenced library that the system intelligently draws from per-frame.

The Continuity Anchor Problem
Even with good multi-view coverage, there's a continuity risk: if shot 3 and shot 7 are both from the same angle in the same room, their backgrounds should look identical — same wall color, same furniture placement, same lighting. But if they were generated independently (even with the same reference image), subtle drift happens.
The solution here overlaps with the non-adjacent frame continuity reference feature already discussed — generated background frames that "lock" a particular view of a location should be reusable as references for subsequent shots that share that angle. Once you've generated a good background for camera position A, that output frame becomes the reference for every future shot in camera position A, not the original asset image.

Open Questions to Resolve Before Building

How many views should be required vs. optional? Requiring too many creates friction; requiring too few defeats the purpose. Probably: one required establishing + one eye-level, rest optional but flagged as recommended based on shot list analysis.
Who generates the multi-view images? Options:

User uploads all of them manually (high quality, high friction)
User uploads one, system generates the others via agentic image generation (lower friction, quality risk)
Hybrid: user uploads what they have, system fills gaps with generated views flagged as AI-inferred


How does sub-location tagging interact with the beat sheet / script? If the script says characters move to the kitchen, should the system automatically flag that a kitchen sub-location view is needed? This kind of story-aware asset gap detection could be very powerful.
How do we handle locations that are entirely AI-generated from a text description? No uploaded reference at all — just a description. Does the system generate the full multi-view set upfront? Or on-demand as shots require them?
