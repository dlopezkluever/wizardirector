## Master Spec Review — Issues, Gaps & Questions

---

### Schema & Data Model

**1. `is_primary` fallback logic is ambiguous**
The spec defines `is_primary` as "the default fallback view (one per location)" but also defines the establishing view as the always-included spatial context image in the 2-ref prompt manifest. These are doing two different jobs. Right now if a shot has no direction match, it falls back to `is_primary` — but if the primary happens to be an overhead establishing shot, you're sending an aerial reference to a ground-level shot, which actively misleads the generator. The spec doesn't clarify whether `is_primary` should be the establishing view or the most common eye-level direction. This needs a decision.

**2. No unique constraint on `(project_asset_id, name)` justification**
The spec includes `UNIQUE(project_asset_id, name)` which is correct, but `name` is defined as a system key (`"establishing"`, `"direction_1"`, etc.). The spec doesn't address what happens if a user wants *two* establishing shots — say, a day version and a night version of the same location. Is the name system flexible enough, or does it need a naming convention like `"establishing_day"` / `"establishing_night"`?

**3. `established_from_scene` is a TEXT field storing a human-readable string**
The spec uses `"Scene 2, Shot 3"` as the example value. This is fine for display, but if you ever want to navigate from a location view back to the source frame, or programmatically query "which scenes have produced established views," a string is the wrong type. Consider storing a FK to the actual shot or scene record alongside the display string, or at minimum storing it as structured JSON.

---

### Pipeline Logic

**4. Stage 5 direction generation has an implicit dependency not called out**
The view generation strategy states: "Send the establishing/primary image as a style reference alongside a text prompt describing the desired view." But what if the user hasn't yet uploaded or generated an establishing image when they click generate on Direction 1? The spec never guards against this. Either the establishing view needs to be a soft requirement before direction generation is available, or the spec needs to define a fallback (e.g., use the asset's master image if no establishing exists yet).

**5. Stage 7 LLM direction assignment + no Stage 5 views yet**
The Stage 7 prompt is supposed to inject available camera directions as context so the LLM can assign `camera_direction_id` per shot. But the spec explicitly says Stage 5 is not a gate and users can leave with zero views. If Stage 7 runs with no views defined, the LLM gets no direction context — the spec doesn't define what Stage 7 does in this case. Does it output shots with null `camera_direction_id`? Does it invent its own directional logic? This needs a defined behavior for the no-views case.

**6. Coverage Advisory triggers on incomplete data**
The Stage 8 coverage panel groups shots by assigned direction and flags gaps. But if Stage 7 ran without any direction context (see above), many shots will have null `camera_direction_id`. The coverage panel will either show everything as unmatched/unassigned or crash trying to group by null. The spec needs a third coverage state beyond ✅/⚠️ to handle "direction never assigned" as distinct from "direction assigned but no image."

**7. Reactivity across stages is mentioned but never specified**
In Stage 7, 8, 9, and 10, direction assignments are described as "editable" and "reactive everywhere." The spec never defines what reactive means in practice. If a user changes a direction assignment in Stage 9, does it update the shot record in the DB immediately? Does it only persist on save? What happens to already-generated frames that used the old assignment? This is a meaningful state management question that needs at least a directional answer in the spec before building.

---

### Prompt Generation

**8. The 2-ref limit assumption needs validation for mixed-asset shots**
The spec states "2 location reference images is the sweet spot" and the example manifest shows 4 total references: 1 character, 2 location, 1 prop. But scenes often have 2-3 characters plus multiple props. The spec doesn't define how the 2-location-ref budget interacts with the total reference count. If a shot has 3 characters and 2 props, do the location refs get dropped? Is there a priority order? The manifest-building logic in `buildNumberedImageManifest()` needs explicit priority rules.

**9. `REFERENCE_TYPE_STYLE` for location refs — delta description interaction**
The graceful degradation strategy says: when the reference doesn't match the shot angle, include a delta description in the prompt. But `REFERENCE_TYPE_STYLE` is already a weaker reference type than `REFERENCE_TYPE_SUBJECT` — it captures palette and tone, not structure. When you're also asking the generator to reframe from eye-level to high-angle, you're asking a style reference to do structural work it's not designed for. The spec could acknowledge this ceiling more explicitly so expectations are set correctly when delta descriptions are in play.

**10. The inline `[1]` and `[2]` reference ID syntax in the Imagen API example**
The spec's example prompt uses `"A cinematic frame of [2] standing in the [1] style kitchen..."` with corresponding `referenceId: 1` and `referenceId: 2` in the API payload. This needs to be verified against Google's actual Imagen API documentation for how inline reference IDs are cited within the prompt string — if the API expects a different citation format, every generated prompt will be malformed.

---

### UX & Feature Completeness

**11. The "Lock as Established View" flow has an unaddressed conflict case**
The spec describes the proactive lock suggestion when a frame fills a coverage gap. But it only briefly mentions the case where a direction already has a user-uploaded reference: "the lock option is still available but not proactively suggested." It doesn't define whether locking replaces the existing reference, coexists as an alternative, or the user gets to choose. For something described as a "core feature," this decision path needs to be fully defined.

**12. Scene-specific view overrides are introduced in Stage 8 without a data model**
The spec mentions: "Stage 8 can also add scene-specific view overrides (e.g., 'this scene's kitchen has smoke damage')." This is a meaningful feature — it implies a location view can behave differently per scene. But the current `location_views` table has no scene-scoping column. There's no data model for this at all. Either this needs a `scene_id` column (or a separate override table), or it needs to be explicitly deferred to future scope.

**13. The batch generation review flow is described for Stage 8 but not for Stage 5**
Stage 5 also has a "Suggest Views" and generate flow, but the spec only fully describes the batch generation confirmation UX for Stage 8. Stage 5 presumably works the same way — but if it's different (e.g., more upfront, less shot-informed), that distinction should be explicit.

---

### Open Questions Worth Answering Before Building

- If a project has 15 sub-locations and each has 3 direction views, that's 45 images before a single frame is generated. Is there a plan for communicating or managing that asset creation burden to the user upfront?
- The spec defers zone hierarchy to future scope, but the flat model's limit is implicitly a location with a large number of distinct areas (a mansion, a ship, a school). At what point does flat become untenable, and does the spec need to define that threshold even if the solution is deferred?
- Established views accumulate over production. The spec doesn't address what happens when a user wants to *replace* a locked established view — either because a later frame looks better or because the story changed. Is there an "unlock" or "re-establish" flow?
