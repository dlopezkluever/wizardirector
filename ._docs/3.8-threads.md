● Step 4 — Things You May Have Missed

  Before I write the planning docs, here are adjacent concerns worth flagging:

  1. Supabase URL expiration (systemic risk for 4D.2)
  The reference_image_order JSONB stores raw image URLs. If Supabase uses signed URLs with expiration, these URLs may be    
  stale by the time Stage 10 tries to download them. NanoBananaClient would silently skip them. This could be the primary   
  reason frames don't reflect assets. Fix: either use permanent public URLs, or re-resolve URLs at generation time.

  2. Silent failure in NanoBananaClient
  When reference image downloads fail, errors are logged to console but never surfaced to the user. Users have no way to    
  know their frames were generated without asset influence. Worth adding: a warning count in the frame generation response  
  ("3 of 5 reference images failed to load").

  3. Location multi-angle requires prompt generation coupling
  Adding named location shots isn't just a data model + UI change. promptGenerationService.ts needs a location-to-shot      
  mapping system (analogous to mapCameraToAngleType for characters). This includes: which named location shot best matches a   given shot's camera/setting.

  4. Sequencing matters
  - 4D.2 (fix asset inheritance) must come before 4C (structured prompts) — no point improving prompt structure if reference   images aren't reaching the API
  - 4B.4 (shot list iteration) should come before 4C since 4C consumes shot list data
  - Frame prompt limit changes should ship with or after 4C

  5. Shot asset assignment auto-population
  autoPopulate() creates throughout for ALL assets × ALL shots by default. This means every location/character/prop appears 
  in every shot's reference manifest — potentially flooding the image API with irrelevant references. The UI improvement you   mentioned could include smarter defaults.
