# Phase 3: Location Asset Multi-Shot System (Task 3)

## Core Goal
Allow location assets to have multiple named reference shots (aerial overview, room corners, hallway entrance, etc.) so that frame generation can use contextually appropriate background references instead of guessing from a single image.

---

## Problem Statement
A single location image cannot represent all the angles and areas of a space. When a scene requires a shot from an angle not covered by the single reference, the image generation model guesses — and guesses badly. A kitchen shot from above should look like the same kitchen as the eye-level shot, but currently there's no connection between them.

---

## Current State

### What Exists
- **Angle variants** (`asset_angle_variants` table): Support for front/side/three_quarter/back angle images per asset. Used by `enrichAssetsWithAngleMatch()` in prompt generation to select the best reference per camera angle.
- **Camera angle detection**: `parseCameraField()` and `mapCameraToAngleType()` extract shot type and angle from the camera field, then match to available angle variants.
- **Location asset images**: Single `image_key_url` per location in Stage 5. Single scene instance image in Stage 8.

### What Does NOT Exist
- Named sub-locations or spatial zones (rooms, areas, vantage points)
- Multi-image location coverage beyond the 4 fixed angle types
- Batch generation of location angles from a base image
- Semantic matching of shot descriptions to location sub-areas

### Gap Analysis
The existing 4-angle system (front/side/three_quarter/back) was designed for characters and props (rotating around a subject). Locations need a different model: named spatial zones that map to camera setups. "Aerial overview", "corner booth", "hallway entrance" are not rotations of the same subject — they're different vantage points within a space.

---

## Implementation Notes

### Data Model Extension

New concept: **Location Shots** — named reference images for specific vantage points within a location asset.

```typescript
interface LocationShot {
  id: string;
  asset_id: string;           // Parent location asset
  name: string;               // User-defined: "aerial_overview", "corner_booth", etc.
  description: string;        // What this vantage point shows
  image_key_url: string | null;
  angle_type?: string;        // Optional: maps to existing angle system
  is_primary: boolean;        // The "default" shot if no specific match
  generation_attempts: LocationShotAttempt[];
}
```

New DB table: `location_asset_shots` (or extend `asset_angle_variants` with a `name` field and location-specific metadata).

### User Workflow

**Stage 5:**
1. User creates/extracts a location asset with a primary image (existing flow)
2. New UI section: "Location Coverage" — shows grid of named shots
3. User can:
   - Add a named shot (type a name like "hallway_entrance")
   - Upload an image for it
   - Generate an image for it (using the primary location image as reference + the shot name/description as prompt guidance)
   - **Batch generate**: Select multiple empty shot slots, generate all from the primary image

**Stage 8:**
- Location shots appear in the master reference carousel (in addition to the primary image)
- Scene-specific location shots can be added (e.g., "this scene's version of the kitchen has a broken window")

**Stage 9 (Prompt Generation):**
- `enrichAssetsWithAngleMatch()` extended: for locations, also check `location_asset_shots` for name-based matching
- Matching heuristic: parse the shot's `setting` and `camera` fields, match against location shot names/descriptions
- If a match is found, use that location shot's image as the reference instead of the generic location image

### Batch Generation Flow

1. User has a primary location image they're happy with
2. Clicks "Generate Coverage" or "Batch Generate Angles"
3. System proposes a set of common vantage points based on the location type:
   - Interior: wide establishing, detail corner A, detail corner B, overhead, through-doorway
   - Exterior: wide establishing, street-level, aerial, approach, detail
   - User can edit/add/remove from the proposed list
4. For each slot: generate using primary image as reference + vantage point description as prompt
5. User reviews results, regenerates any that don't look right

### Matching Heuristic for Prompt Generation

When building reference images for a shot that includes a location:
1. Parse shot's `camera` field and `setting` field
2. Check if any `location_asset_shots` match by name or description (fuzzy match via keyword overlap or LLM classification)
3. If match: use that shot's image
4. If no match: fall back to primary location image (existing behavior)
5. [UNRESOLVED] Whether to use LLM for matching (expensive, accurate) or keyword heuristic (cheap, less accurate)

## Dependencies
- No hard dependency on Phases 0-2
- **Phase 0B confirmed**: Reference images correctly reach the image gen API. URL priority (`matched_angle > scene_instance > master`) is intact. Identity refs prepended before style refs.
- The matching heuristic in Stage 9 should be built after Phase 4 (frame prompt quality improvements) since both touch `promptGenerationService.ts`

## Notables
- This is a significant scope expansion of the asset system. Consider MVP: just named location shots with manual image upload/generation, WITHOUT the smart matching heuristic. Manual selection of which location shot to use per scene shot is simpler and still valuable.
- Batch generation quality depends heavily on the image gen model's ability to maintain spatial consistency from a single reference. Test this with the current provider before building the full batch UI.
- [UNRESOLVED] Whether location shots should exist at the Stage 5 level (global to project) or Stage 8 level (per scene). Recommendation: Stage 5 level, with Stage 8 allowing scene-specific overrides (same pattern as character descriptions).
- Storage costs: each location may have 5-10 reference shots. Monitor Supabase storage usage.
