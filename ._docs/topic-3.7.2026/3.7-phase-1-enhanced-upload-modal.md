# Phase 1: Enhanced Upload Modal (Task 1)

## Core Goal
Upgrade the existing image upload flow in Stages 5 and 8 so that after uploading an image, the user has a single modal where they can: reconcile the description, edit the image via text instructions, apply the project's visual style, remove the background (white), and regenerate. The end goal for the user: an image they like + a description that matches it.

---

## Problem Statement
When a user uploads an image for an asset, the auto-extracted description often doesn't match their intent, and the image itself may need modifications (wrong outfit, wrong style, has a busy background). Currently, Stage 5 has a basic 3-button modal (keep/replace/merge description) that doesn't support iterative editing. Stage 8 has no equivalent reconciliation flow at all.

---

## Current State

### Stage 5 Upload Flow (`Stage5Assets.tsx`)
1. User clicks "Upload" -> file picker
2. `handleUploadImage()` sends file to backend
3. Backend stores image in Supabase `asset-images` bucket, creates generation attempt
4. Frontend calls `projectAssetService.analyzeImage()` (Gemini Vision extracts description)
5. `ImageDescriptionModal` opens with 3 options: Keep Current / Replace with Extracted / Use Merged
6. User picks one, modal closes. Done.

**Limitations**: No way to iteratively edit. No "edit image" capability. No style application. No background removal. No regen from the modal.

### Stage 8 Upload Flow
- Upload exists for scene instance images via `VisualStateEditorPanel`
- No description reconciliation modal at all
- Uploaded image becomes the scene instance image directly

### Existing Infrastructure
- `assetDescriptionMerger.ts`: LLM-powered description merge (used by current modal)
- `projectAssetService.analyzeImage()`: Gemini Vision image analysis
- `projectAssetService.generateImage()`: Regen from description (with polling)
- Reference-based regen exists for global library clones (`referenceImageUrl` param)
- Visual style capsule available from Stage 5 locked state

## Implementation Notes

### Enhanced Modal Design

The upgraded modal replaces the current `ImageDescriptionModal`. It should be a multi-section panel:

**Section 1: Description Reconciliation**
- Left: "Current Description" (read-only, the description before upload)
- Right: "Extracted Description" (read-only, from Gemini Vision analysis)
- Below: "Final Description" (editable textarea, pre-populated with LLM merge of both)
- User edits the final description to get it exactly right

**Section 2: Image Actions** (row of action buttons)
- **"Edit Image"** button: Opens a text input where user types what to change (e.g., "change suit to orange jumpsuit", "add scar on left cheek"). Triggers a generation using the uploaded image as reference + the edit instruction as prompt modifier. Result appears in the modal's image preview area.
- **"Apply Visual Style"** button: Regenerates the uploaded image with the project's visual style capsule applied (e.g., photo -> Pixar style). Uses uploaded image as reference + visual style capsule + current description.
- **"Remove Background"** button: Regenerates the image with explicit "white background, isolated subject" prompt directive. Only shown for characters, props, and extras (NOT locations).
- **"Regenerate from Description"** button: Standard regen using the final description text + visual style capsule. No reference image (fresh generation from text).

**Section 3: Image Preview**
- Shows the current image (initially the uploaded one)
- Updates when any action produces a new image
- Carousel of attempts if multiple actions are performed

**Section 4: Confirm**
- "Accept" button: Sets the current image as the asset's active image, saves the final description
- "Cancel" button: Reverts to state before upload

### Intent Handling (Implicit)
No explicit "Full Replacement" vs "Starting Point" toggle. Instead:
- Upload always triggers the enhanced modal
- If user is happy with the image as-is, they just edit the description and hit Accept
- If user wants to iterate, they use Edit Image / Apply Style / Remove BG buttons
- The "Apply Visual Style" and "Remove Background" actions automatically include white background for non-location assets (characters, props, extras)

### White Background Auto-Application
`injectBackgroundContext()` in `ImageGenerationService.ts` already appends `. Isolated on a plain white background, no environment, no other characters or objects.` for non-location asset types (`scene_asset`, `master_asset`, `angle_variant`, `transformation_post`). No new work needed for standard regen flows. The new `edit-image` endpoint must also call this method or use the same job types to inherit the behavior.

### New Backend Endpoint: Edit Image
```
POST /api/projects/:projectId/assets/:assetId/edit-image
Body: {
  referenceImageUrl: string,    // The uploaded/current image to edit
  editInstructions: string,     // What to change ("add scar", "change to jumpsuit")
  description: string,          // Full asset description for context
  visualStyleCapsuleId?: string, // Optional: apply style
  whiteBackground: boolean,     // Auto-set for non-location assets
  assetType: string             // To determine aspect ratio
}
Returns: { jobId: string, status: string }
```

Same polling pattern as existing `generateImage`. Backend constructs a prompt that combines the edit instructions with the description, attaches the reference image, and includes white background directive if applicable.

A parallel endpoint for Stage 8 scene assets:
```
POST /api/projects/:projectId/scenes/:sceneId/assets/:instanceId/edit-image
Body: { same as above, plus sceneId context }
```

## Notables
- The "Edit Image" feature is essentially image-to-image with text guidance. The quality depends heavily on the image generation provider's support for reference images + text instructions. Verify this works with current Flux/Gemini provider before committing to the UX.
- White background auto-application means every regen for non-location assets will include the directive. If this produces artifacts for certain asset types, may need to make it toggleable later.
- The modal should be designed as a shared component (`EnhancedUploadModal`) from the start since it's used in both Stage 5 and Stage 8. Stage-specific differences (description source, generation endpoint) are passed as props.
