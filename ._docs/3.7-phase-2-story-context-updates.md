# Phase 2: Story-Aware Description & Tag Updates (Task 2)

## Core Goal
Add the ability for users to update asset descriptions and status tags in Stage 8 based on what's actually happening in the story at that scene. Two entry points: a per-asset button in the editor panel, and a bulk button in the sidebar for multiple assets at once.

---

## Problem Statement
Asset descriptions inherited from Stage 5 are static. They describe the asset in general terms ("Alice: tall woman, brown hair, blue dress") but don't reflect scene-specific conditions ("Alice is now soaked from the rain, dress torn, visibly exhausted"). Users must manually figure out and type these changes. The script, treatment, and beat sheet already contain this information — an agentic tool should be able to infer it.

---

## Current State

### What Exists
- **Description override system**: `SceneAssetInstance.description_override` allows per-scene overrides of master description. `effective_description` resolves override > inherited > master.
- **Version history**: `textFieldVersionService` tracks description versions per field, allows cycling through past versions.
- **Status tags**: `StatusTagsEditor` component with freeform tag input. Tags stored on `SceneAssetInstance.status_tags`.
- **AI Detection button**: Discovers new assets for a scene. Uses LLM to analyze script for relevant assets. Does NOT infer conditions of existing assets.
- **Story data accessible**: Script (Stage 2), treatment (Stage 3), beat sheet (Stage 3), shot list (Stage 7) — all queryable from backend.

### What Does NOT Exist
- No "Update from Story Context" button
- No agentic tool that reads story context to propose description/tag updates
- No bulk update flow for multiple assets
- AI detection and condition inference are completely separate concerns (per user decision)

---

## Implementation Notes

### Per-Asset Button: "Update from Story Context"

**Location**: `VisualStateEditorPanel.tsx`, next to the description override textarea. A button labeled something like "Infer from Story" or "Update from Context".

**Flow**:
1. User selects an asset in Stage 8, clicks the button
2. Frontend calls backend: `POST /api/projects/:projectId/scenes/:sceneId/assets/:instanceId/infer-context`
3. Backend assembles story context:
   - Scene's script excerpt (from Stage 2 screenplay, filtered to this scene)
   - Scene's beat sheet entry (from Stage 3)
   - Scene's treatment section (from Stage 3)
   - Shot list entries for this scene (from Stage 7) — especially `action` and `dialogue` fields
   - Asset's current `effective_description` and `status_tags`
   - Asset's master description (from Stage 5)
4. Backend sends to LLM with a prompt like:
   ```
   You are analyzing a scene from a screenplay to determine the visual condition
   of a specific asset (character/prop/location) in this scene.

   Given:
   - Asset: {name} ({asset_type})
   - Master description: {master_description}
   - Current scene description: {effective_description}
   - Current status tags: {status_tags}

   Scene context:
   - Script: {scene_script_excerpt}
   - Beat sheet: {beat_entry}
   - Treatment: {treatment_section}
   - Shot list actions: {shot_actions}

   Determine:
   1. An updated visual description that reflects the asset's condition IN THIS SCENE
      (what they're wearing, their physical state, emotional state, any changes from master)
   2. Suggested status tags (short visual modifiers like "muddy", "bleeding", "formal attire")

   Return JSON:
   {
     "suggested_description": "...",
     "suggested_tags": ["tag1", "tag2"],
     "reasoning": "Brief explanation of what story context informed these suggestions"
   }
   ```
5. Backend returns suggestions to frontend
6. Frontend displays in a preview panel:
   - Current description vs suggested description (side by side or diff view)
   - Current tags vs suggested tags
   - Reasoning text (collapsible)
   - "Accept Description" / "Accept Tags" / "Accept Both" / "Dismiss" buttons
7. If accepted:
   - Description: saved as new `description_override` version via `textFieldVersionService`
   - Tags: merged with or replace existing `status_tags`
   - Both become new save states (not replacements — prior versions accessible)

### Bulk Button: "Bulk Update from Context"

**Location**: Stage 8 sidebar (`SceneAssetListPanel.tsx`), near the existing AI Detection button but clearly separate. Only enabled when assets are selected via checkboxes.

**Flow**:
1. User selects multiple assets via checkboxes in the sidebar
2. Clicks "Bulk Update from Context" button
3. Frontend calls: `POST /api/projects/:projectId/scenes/:sceneId/bulk-infer-context`
   - Body: `{ instanceIds: string[] }`
4. Backend runs the same inference for each selected asset (can batch into a single LLM call with all assets for efficiency, or parallelize individual calls)
5. Returns array of suggestions, one per asset
6. Frontend opens a **Review Modal**:
   - List of assets, each expandable
   - For each: current vs suggested description, current vs suggested tags, reasoning
   - Per-asset accept/reject toggles
   - "Accept All" / "Reject All" buttons at top
   - "Apply Selected" button at bottom
7. User reviews, toggles, and applies

### Review Modal Design

```
+----------------------------------------------------------+
|  Bulk Story Context Update                    [Apply All] |
+----------------------------------------------------------+
| [x] Alice (character)                                     |
|     Description: "Alice, soaked from rain, torn blue..."  |
|     Tags: +muddy +exhausted +torn_clothing                |
|     Reason: "Scene 4 script describes heavy rainfall..."  |
|                                                           |
| [x] Bob (character)                                       |
|     Description: "Bob in formal black suit, confident..." |
|     Tags: +formal_attire +smiling                         |
|     Reason: "Beat sheet indicates Bob arrives at the..."  |
|                                                           |
| [ ] Kitchen Table (prop)                    [dismissed]   |
|     Description: (no changes suggested)                   |
|     Tags: (none)                                          |
|                                                           |
+----------------------------------------------------------+
|                              [Cancel]  [Apply Selected]   |
+----------------------------------------------------------+
```

### Backend Endpoint Design

**Per-asset:**
```
POST /api/projects/:projectId/scenes/:sceneId/assets/:instanceId/infer-context
Returns: {
  suggested_description: string,
  suggested_tags: string[],
  reasoning: string
}
```

**Bulk:**
```
POST /api/projects/:projectId/scenes/:sceneId/bulk-infer-context
Body: { instanceIds: string[] }
Returns: {
  results: Array<{
    instanceId: string,
    assetName: string,
    assetType: string,
    current_description: string,
    suggested_description: string,
    current_tags: string[],
    suggested_tags: string[],
    reasoning: string
  }>
}
```

### Story Context Assembly

New backend service method (likely in `contextManager.ts` or a new `storyContextService.ts`):

```typescript
async function assembleSceneStoryContext(projectId: string, sceneId: string): Promise<{
  scriptExcerpt: string;
  beatEntry: string;
  treatmentSection: string;
  shotActions: string[];
}>
```

This queries:
- Stage 2 data: screenplay text filtered to the scene
- Stage 3 data: beat sheet and treatment for the scene
- Stage 7 data: shot list actions/dialogue for the scene

This context is reused across all assets in a bulk call (fetched once, used N times).

## Dependencies
- No hard dependency on Phase 1 (this is independent feature work)
- **Phase 0 confirmed**: `effective_description` IS used correctly in generation. Status tags were missing from scene instance image gen prompts — now fixed. Updating descriptions and tags will correctly affect subsequent image generations.

## Notables
- The LLM prompt for context inference should be tuned carefully. Over-eager updates (changing descriptions when nothing meaningful happened) will annoy users. The reasoning field helps users decide whether to accept.
- Bulk calls with many assets in a single scene could be expensive (LLM tokens). Consider batching multiple assets into one LLM call with structured output, rather than N separate calls.
- Status tag suggestions should be ADDITIVE by default (merged with existing tags), not replacing. The review modal should make this clear.
- The version history system (`textFieldVersionService`) means accepted suggestions are non-destructive — users can always revert to prior description versions.
