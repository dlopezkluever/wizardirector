  ---
  Current System Summary

  The current location system treats locations as single-image assets — identical to how characters/props work, just with 
  a 16:9 ratio. Key gaps:

  - One image per location (master) + optional scene-level override
  - No angle variant system for locations — only characters have front/side/three_quarter/back
  - enrichAssetsWithAngleMatch() in promptGenerationService.ts:115-139 only operates on characters; locations always fall 
  back to the single reference image
  - Shot setting field is free-text matched to location by name — no spatial awareness
  - determineContinuityLink() detects same/different location but doesn't consider sub-positions within a space
  - Frame prompts include location description text but rely on one reference image regardless of camera angle

  Your concern notes nail the fundamental problem: locations aren't objects, they're spaces. The existing 4-angle rotation   model was built for objects you look at, not environments you look from within.

  ---
  Brainstorm: A Location Coverage Architecture

  Here's my thinking, organized from foundational to ambitious:

  1. Hierarchical Location Model (Core Data Redesign)

  Replace the "one image = one location" model with a spatial hierarchy:

  Location Asset (master)
  ├── Establishing View (wide/aerial — the "identity" of the space)
  ├── Zone: Main Area
  │   ├── View: eye-level-primary (the default shot)
  │   ├── View: eye-level-reverse (looking back)
  │   └── View: detail-fireplace
  ├── Zone: Kitchen Doorway
  │   └── View: eye-level-from-living-room
  └── Zone: Hallway
      └── View: looking-in

  Each View is a named reference image with metadata:
  - view_type: establishing | eye_level | detail | overhead | approach
  - camera_distance: wide | medium | close
  - camera_height: eye_level | high_angle | low_angle | overhead
  - zone_label: optional sub-location tag ("kitchen_area", "by_the_window")
  - is_primary: the default fallback view

  This differs from the Phase 3 doc's LocationShot by adding the zone grouping layer. Zones let the system reason about   
  where in the space a shot happens, not just what angle.

  2. Shot-List-Driven Gap Analysis ("Coverage Report")

  Before entering generation (between Stage 8 and Stage 10), the system analyzes ALL shots for a location across the      
  scene:

  1. Parse each shot's camera field (angle, distance) and setting/action fields (spatial cues like "walks to the window", 
  "stands in the doorway")
  2. Cluster shots into view-groups (e.g., 6 shots at eye-level medium, 2 at high-angle wide, 1 looking through doorway)  
  3. For each cluster, check if a matching location view exists
  4. Produce a Coverage Report:
    - "8 shots use eye-level medium — covered by eye_level_primary"
    - "3 shots use high-angle wide — no reference available (quality risk)"
    - "2 shots describe characters near the window — no zone reference for window area"
  5. User can then create missing views before generation, or accept the risk

  This is extremely valuable because it's proactive — it tells you what's missing before you waste credits generating bad 
  frames.

  3. Deterministic Shot-to-View Assignment

  In Stage 9 (prompt segmentation) or a new sub-step, each shot gets assigned to a specific location view:

  1. AI-suggested: System analyzes the shot's camera/setting/action and picks the best matching view
  2. User-confirmable: User reviews assignments in a table, can override
  3. Stored: Assignment persists as shot_location_view_id on the shot-asset assignment
  4. Used at generation time: enrichAssetsWithAngleMatch() extended to pull the assigned view's image instead of the      
  generic location image

  This replaces the current "always use the same image" behavior with per-shot view selection. The matching heuristic can 
  be as simple as:
  - Parse camera distance + height → match to view's camera_distance + camera_height
  - Check action text for zone keywords → match to view's zone_label
  - If no match → fall back to primary view

  No LLM needed for the basic version — keyword/metadata matching is deterministic and fast.

  4. Generated Frame Caching ("Established Views")

  This addresses your Continuity Anchor Problem directly:

  1. After a frame is generated and the user approves it, the system asks: "Lock this as an established view for
  [Location] from [angle]?"
  2. If locked, the generated frame is stored as a new location view reference
  3. All subsequent shots from the same angle at that location use this generated frame as their reference instead of the 
  original asset image
  4. The location's view library grows organically during production

  Why this is powerful: The first time you generate a kitchen at eye level, the AI invents details. The second time, it   
  references its own prior output — achieving pixel-level consistency without the user uploading anything extra.

  Implementation detail: This could integrate with the existing selectMasterReference() / getReferenceChain() system in   
  sceneAssetService.ts:606-669.

  5. Multi-Reference Composition in Prompts

  Currently, each asset contributes ONE image to the reference manifest. For locations, I'd suggest providing 2-3
  reference images per frame:

  1. Primary: The best-matching view for this shot's camera angle
  2. Establishing: Always include the wide establishing shot (gives spatial context and color palette anchor)
  3. Detail (optional): If the shot calls for a close-up or specific area, include a relevant detail view

  The prompt manifest (built in promptGenerationService.ts:169-213) would say:
  Image #1: Kitchen - eye level primary (location, MAIN REFERENCE)
  Image #2: Kitchen - establishing wide (location, SPATIAL CONTEXT)
  Image #3: Kitchen - detail stovetop (location, DETAIL REFERENCE)

  This gives the model more constraints to work from — it's not inventing the room from one image, it's synthesizing from 
  a coherent set.

  6. Batch View Generation from Primary Image

  For the view creation workflow:

  1. User provides or generates ONE good establishing shot
  2. Clicks "Generate Coverage"
  3. System proposes views based on location type:
    - Interior: establishing, eye-level primary, eye-level reverse, 2 detail focal points
    - Exterior: establishing, street-level, approach, aerial, detail
  4. For each proposed view: generates using the establishing shot as reference + the view description as prompt
  5. User reviews, approves/regenerates each
  6. Approved views populate the location's view library

  Quality risk: AI-generated alternate angles from a single image can be inconsistent. Mitigation: always send the        
  establishing shot alongside each generation request as an anchor, and include the existing location description in the  
  prompt.

  7. Story-Aware Sub-Location Detection

  The user's concern notes mention this: if the script says characters move to the kitchen doorway, the system should     
  detect that as a sub-location need.

  Implementation:
  1. During Stage 4 (dependency extraction) or Stage 7 (shot list creation), parse action/direction text for spatial      
  movement cues
  2. Tag shots with inferred zone_label values
  3. Feed these into the Coverage Report
  4. Flag: "Characters move to 3 distinct areas within 'Kitchen' — consider adding zone references"

  This bridges narrative → spatial awareness without requiring the user to manually tag zones.

● Excellent research results. Here are the findings that directly impact our design:

  ---
  Research Findings & Implications

  1. Google Has No "Location" Reference Type

  Critical discovery: Imagen's REFERENCE_TYPE_SUBJECT only supports PERSON, ANIMAL, PRODUCT. There's no "place" or        
  "environment" subject type. For locations, we need to use:
  - REFERENCE_TYPE_STYLE — captures visual tone, color palette, atmosphere
  - First-frame mode in Veo — but can't combine with reference images
  - Detailed prompt descriptions repeated identically across shots (the "scene bible" pattern)

  Impact on our design: When sending location views as reference images for frame generation, we'd use them as style      
  references, not subject references. This actually works well for environments — we want the model to capture the feel   
  and visual identity of the space, not reproduce an exact object.

  2. Veo Can't Combine First-Frame + Reference Images

  This means the generated frame IS the environment anchor for video generation. Veo gets the first frame and extends it  
  into motion — no additional reference images alongside. This makes our Stage 10 frame quality even more critical. Every 
  investment in better location view matching directly improves video output quality.

  3. 2-3 References Is the Sweet Spot

  Research consistently shows diminishing returns and quality degradation beyond 3-4 reference images. Our plan of best   
  match + establishing = 2 location refs is well-calibrated per the research. Going beyond that would actually hurt       
  quality.

  4. AI Is Unreliable at Generating Alternate Room Angles

  This is important for the batch view generation feature. The research says AI works well for simple product rotations   
  but poorly for complex environments — wrong proportions, spatial inconsistencies, hallucinated furniture.

  Implication: We should still offer batch view generation, but temper expectations. User uploads and manual curation are 
  more reliable than automated generation. The UI should make uploading easy and generation optional. We should frame     
  generation as "starting point, expect to curate" not "click and done."

  5. "Hero Frame" Pattern Is Industry Standard

  The "Established Views" concept (lock a generated frame as future reference) is exactly what practitioners recommend.   
  Generate one good frame, lock it, reuse it. This is the single most impactful technique for consistency according to the   research.

  6. "Scene Bible" Pattern Validates Our Approach

  The most reliable approach for environment consistency: lock descriptors (lighting, color grade, architecture,
  materials) into text and repeat them identically in every prompt. Our existing assetContext system does this. We should 
  strengthen it with more structured, repeatable location descriptors.

## Future Considerations (Not In Scope)

These are recognized opportunities that may be worth pursuing later, but are explicitly **not part of this specification**:

- **Zone hierarchy**: If the flat views model proves insufficient for very complex locations (e.g., multi-room mansions), views could be grouped into named zones. The `location_views` table could gain a `zone_label` column for grouping without a separate table.
- **LLM-based matching**: If metadata matching proves too coarse, a lightweight LLM classification step could improve shot-to-view matching accuracy. Build the metadata matcher first and evaluate before adding LLM cost.
- **ControlNet / IP-Adapter integration**: For maximum environment control, these Stable Diffusion ecosystem tools offer granular style and structure conditioning. Requires separate infrastructure from Google's APIs.
- **3D environment pre-visualization**: Using tools like Unreal Engine to generate 360° panoramas of environments, then applying style transfer for inherently consistent backgrounds.
- **Auto-lock established views**: Automatically locking the first approved frame per direction. Currently manual-only to preserve user control; could be offered as a preference toggle.
